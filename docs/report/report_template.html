2. Architecture

{{ARCH_SVG}}

Figure 1. One turn of RecallBot, labelled with the function names in src/. Solid arrows: the turn's data flow. Green boxes: the four memory types (short-term, semantic, episodic, procedural) and where each lives. Session A and Session B run as separate processes; only memory/ and db/ carry information between them.

Every customer message passes through rule-based NLU (one intent plus entities), the state tracker (task slots, clarification, pending confirmation, write authorisation) and the dialogue manager, which calls tools and writes a deterministic draft (the authoritative text for actions and references). The memory manager extracts facts, records episodes and retrieves memories for the turn; the context assembler fits system prompt, tools, workflow step, state, draft, memories, knowledge-base chunks and trimmed history into 1,856 input tokens; QwenNLG phrases the reply and keeps every ID. If the model drops a protected value (ID, date, amount) the draft is used instead.

2(a) Pipeline, prompts and procedural memory

NLU is rule-based (normalisation, regular expressions, phrase rules in src/dialogue/nlu.py; no LLM). On 40 labelled utterances (data/nlu_test_cases.json, turns 1–40) it gets 40/40 intents and expected entities right (results/nlu_accuracy.json). This is accuracy on the scripted set the rules were written next to, not an estimate for unseen traffic.

State-tracker fields (DialogueStateTracker): session_id, user_id, turn, last_user_text, current_intent, current_entities, active_task, task_status, slots (order, item, reason, pickup date, window, address, explicit_confirmation), missing_slots, available_order_items, clarification_required, clarification_prompt, pending_confirmation, confirmation_status, pending_action, database_write_authorized, last_tool_result. explicit_confirmation cannot be set by slot filling; it needs a separate "yes" while a concrete pending action exists, and book_slot re-checks order, SKU and slot before writing.

Procedural memory is versioned in skills/: system_prompt_v1.txt (Task 2), system_prompt_v2.txt (Tasks 3–4, compact for the 2,048 window) and return_pickup_workflow_v1.json (the step list); QwenNLG loads them at start-up. The prompts cover persona (calm, concise ShopSphere assistant), scope (orders, delivery, returns, refunds, exchanges), error handling (no invented bookings or references; the exact fallback sentence; ask for the next missing detail; never reveal forgotten data) and format (≤ 90 words, IDs preserved, no JSON or source footer — citations are appended by the code). 3(a) Chunking and indexing

Two chunk sizes, 128 and 512 Qwen3 tokens, with 15 % overlap counted in tokens (19 and 77). Each chunk stores chunk_id, doc_id, section, version, status (active/superseded), effective_from/to, start_char/end_char. Embeddings: BGE-small, CLS pooling, normalised; a chunk longer than BGE's 512-token limit is split and token-weighted-averaged rather than truncated. Index: exact flat inner product — with 84 / 24 chunks a brute-force search is exact and sub-millisecond, so an approximate graph index would only add error and build cost (index/dense_*/index_manifest.json).

3(c) Semantic memory of the user

SemanticMemory stores keyed records {memory_id, user, key, value, source_turn, session, date, status, supersedes, extraction_method} with a deletable flat vector index of the active facts. Extraction (FactExtractor, logged as extract): rules map NLU entities to canonical keys; only when a fact-like turn yields nothing, Qwen returns JSON that is validated (known key format, value grounded in the message, ≤ 80 chars, no secrets). Greetings, small talk, thanks and confirmations never reach extraction.

3(d) Episodic memory

EpisodicMemory keeps time-stamped episodes (type, description, entities, linked memory IDs) with rule-based importance 1–10: booking 9, complaint 8, decision 7, reflection 6, task event 5, preference update 4, preference/forget event 3, small talk 1 (write threshold 3). Retrieval score = wr·R̂ + wi·Î + ws·Ŝ, R = 0.995hours on a logical clock (Session A 21 Nov 10:00, Session B 24 Nov 10:00, +2 min/turn), I = importance/10, S = BGE cosine; each min-max normalised over the candidates (score_episodes()).

Does the prefix reach the minimum? trim: yes (1,100 tokens). hybrid_mem: no — Twist E forced a 334-token prefix, below 1,024. What I would change: not padding. Padding to 1,024 with few-shot examples would raise the GPT-4o bill by $12,683/month (690 extra tokens at $1.25 cost more than 50 % saved on 334) and use 37 % of the 1,856-token input budget. hybrid_mem is already cheaper than cached trim ($72.2 k vs $81.0 k). Better savings: cap reply length (output costs 4× input) and send tool definitions only on tool turns; add genuinely useful few-shot examples only with a larger context window.

4. Limitations and what I would change with one more week

  • Small model, small test set. qwen3:1.7b misreads correct evidence (P11) and adds stray "Missing detail" lines; 16 probes with 1–3 per category cannot separate configurations by one probe. With a week: an extractive draft for policy sequences, a 7–8B model comparison, and 3× more probes, including unscripted paraphrases.
  • Rules fitted to the script. NLU (40/40) and extraction (precision and recall 1.00) were built next to the test conversation; I would measure both on new, held-out conversations and extend the LLM fallback.
  • Episodic ranking still favours the high-importance booking for loosely worded questions (turn 29); I would add type-aware boosts ("problem" → complaint) and tune weights on more than 12 queries.
  • Missing handler: cancellation eligibility (turn 36) has no get_order-backed check, so a KB-only answer can over-promise.
  • Judge: the 1.7B judge does not agree with manual ratings (κ ≤ 0.23); a larger judge with calibration examples would be needed before using it.
  • Scale: one flat index per user is fine locally; at 25,000 users I would move to one HNSW index (M 32, ef 200) with a user filter and an episode retention policy.

A case where the AI's suggestion was wrong. What it suggested: for the 2,048-token context assembler, the assistant counted tokens as len(tokenizer.apply_chat_template(messages, tokenize=True, ...)), assuming the call returns a list of token IDs. How I found out: in the pilot run t3_hm_pilot_A the context-assembly records showed "2 / 1,856 tokens" on every turn, while Ollama's prompt_eval_count in logs/calls.jsonl reported 463–1,506 tokens for the same calls. With transformers 5.x the call returns a BatchEncoding, so len() counted its two keys and the budget check enforced nothing (the log confirmed no pilot prompt had exceeded the budget). What I changed: (1) count encoded["input_ids"]; (2) a plausibility test — the templated total must lie between the sum of the parts and that sum + 120 — so a silent miscount now fails the suite; (3) compared with Ollama on all 26 pilot Session B calls, found a constant +8 (the empty <think> block) and added it as a measured offset. In the official run the count matched Ollama on 51 of 51 chat calls. The pilot stays in the log, labelled as a pilot.

Two smaller corrections of the same kind: the first P11 query rewrite proposed words from the expected answer ("returns centre, inspection, refund"), which would leak the answer into retrieval — I rejected it for a generic topic phrase; and the original forget rule would have treated the probe question "What delivery note did I ask you to forget?" as a forget request — questions can no longer trigger a forget.
